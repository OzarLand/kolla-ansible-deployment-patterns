# From 2025.1 to 2026.1. What changes for a Kolla-Ansible deployment, from the release notes

## Context

2025.1 and 2026.1 are both SLURP releases, so a deployment can go from one to the other in a single skip-level
upgrade; the Kolla-Ansible operating guide for 2026.1 describes the extra preparation. Everything released in
between, in the 2025.2 (Flamingo) and 2026.1 cycles, reaches the deployment at once.

This page lists what a 2025.1 deployment meets on the way, grouped by what the operator has to do. It is built from
the release notes in the Kolla-Ansible source: the notes present on the `stable/2026.1` branch and absent from
`stable/2025.1`, read one by one (97 files), together with the 2025.2 and 2026.1 preludes, the 2026.1 operating
guide, support matrix and sample inventory. It has not been applied to a platform: the release notes say what
changed, not how an upgrade went. First-hand reports are wanted (issue #6).

## Topology

Not specific to a topology. The inventory changes below apply to every deployment that keeps its own copy of the
inventory.

## Network design

See the Neutron rows below: Linux Bridge removed, agent wrappers on by default.

## Storage design

See the Cinder rows below: `cinder-volume` and `cinder-backup` move to the controllers by default.

## Inventory and configuration layout

### Before the upgrade: what must change

| Change | What to do | Release note |
|---|---|---|
| Ansible: 2025.1 supports Ansible 10 to 11 (ansible-core 2.17 to 2.18); 2026.1 supports Ansible 12 to 13 (ansible-core 2.19 to 2.20) | Upgrade Ansible on the deployment host; the operating guide says to do it explicitly for a skip-level upgrade, then run `kolla-ansible install-deps` | `ansible-2.19`, `ansible-2.20` |
| Host operating systems: 2025.1 supports CentOS Stream 9 and 10, Debian 12, Rocky Linux 9 and 10, Ubuntu 24.04; 2026.1 supports CentOS Stream 10, Debian 13, Rocky Linux 10, Ubuntu 24.04 | Move hosts on Debian 12, Rocky Linux 9 or CentOS Stream 9 to a supported OS first | Support matrices of both releases |
| Inventory: group `kolla-toolbox` renamed `kolla_toolbox`; the `common` role renamed `kolla_toolbox` | Rename the group in your inventory and overrides | `rename-kolla-toolbox-role` |
| Inventory: new `kolla_logs` group (log collection split from `common`); `cron` and `fluentd` have their own roles | Add the `kolla_logs` group, as in the 2026.1 sample inventory | `kolla-logs-rename`, `cron-break-out-role`, `fluentd-break-out-role` |
| Cinder: `cinder-volume` and `cinder-backup` now default to the `cinder` group (the controllers) instead of `storage`; new groups `cinder-volume-lvm`, `cinder-volume-multiple`, `cinder-backup-lvm`, `cinder-backup-multiple` | Update inventory overrides; LVM users keep the volume service on the hosts that hold the volume group | `move-cinder-volume` |
| Redis replaced by Valkey | Set `enable_redis: "no"` and `enable_valkey: "yes"` in `globals.yml` before the upgrade; the playbooks migrate the data | `replace-redis-with-valkey` |
| RabbitMQ: upgrades are limited to allowed version paths (`rabbitmq_allowed_upgrades`, for example 3.13 to 4.0, 4.1 or 4.2); a skip-level upgrade may need an intermediate RabbitMQ version | Check the allowed path before upgrading; the `rabbitmq-version-check` task fails with the next intermediate version otherwise | `rabbitmq-42`; RabbitMQ guide |
| Linux Bridge mechanism driver removed, already removed from Neutron | Migrate to ML2/OVS or ML2/OVN before the upgrade | `remove-neutron-linuxbridge` |
| Services dropped: Zun and Kuryr, InfluxDB, Telegraf, Venus, VMware drivers, `ironic-inspector`; legacy (non-rolling) Ironic upgrade | Remove them from the deployment first; InfluxDB and Telegraf containers and configuration are to be removed manually | `drop-kuryr-and-zun`, `drop-influxdb-telegraf`, `drop-venus`, `drop-vmware-support`, `drop-ironic-inspector`, `ironic-drop-legacy` |
| Variables renamed or removed: `lightbits_JWT` → `lightbits_jwt`; `ironic_inspector_kernel_cmdline_extras` → `ironic_kernel_cmdline_extras`; `ironic_inspector_pxe_filter` → `ironic_pxe_filter`; `bifrost_enable_ironic_inspector`, `distro_python_version` and `neutron_legacy_iptables` removed | Update `globals.yml` and overrides | `lightbits-jwt`, `drop-ironic-inspector`, `remove-distro-python-version`, `drop-legacy-iptables` |
| Local changes to the log-rotation cron templates | Re-apply them on the simplified templates | `simplified-cron-templates` |

### What changes by itself during the upgrade

| Change | Consequence to expect | Release note |
|---|---|---|
| MariaDB through HAProxy and `clustercheck` is no longer supported | `kolla-ansible upgrade` deploys ProxySQL and removes the `clustercheck` containers. ProxySQL was already the 2025.1 default; this affects deployments that had disabled it | `drop-clustercheck-and-haproxy-support-for-mariadb` |
| All API services under uWSGI, Apache WSGI support dropped | `glance-tls-proxy` and `neutron-tls-proxy` disappear; TLS is terminated by uWSGI | `uwsgi-glance`, `neutron-uwsgi`, `barbican-uwsgi`, `uwsgi-designate`, `uwsgi-magnum` |
| Neutron follows the upstream layout | New containers `neutron-rpc-server`, `neutron-periodic-workers`, `neutron-ovn-maintenance-worker` | `neutron-uwsgi` |
| Neutron agent wrappers on by default | DHCP, L3 and related agents restart without respawning the main containers; set `neutron_agents_wrappers: "no"` for the old behaviour | `neutron-agent-wrappers-by-default` |
| Horizon behind HAProxy listens on port 8080 | Firewall rules or monitoring that target Horizon's backend port need updating | `horizon-port` |
| ML2/OVS L3 HA no longer sets `ha_vrrp_health_check_interval` | Different failover behaviour when the router's health checks were relied on | `diable_ha_vrrp_health_check_interval` |
| `om_rabbitmq_qos_prefetch_count` raised to 50 | Different message flow per consumer | `qos_prefetch_count_bump` |
| Enterprise Linux hosts: HAProxy and RabbitMQ trust `ca-bundle.crt` instead of `ca-bundle.trust.crt` | Check custom CA handling on EL hosts | `ca-bundle-trust` |
| Horizon session cache uses Valkey when it is enabled | Session behaviour changes with Valkey | `bug-2093414` |
| `kolla-toolbox` uses `clouds.yaml` | `openstack_auth` only carries the Keystone admin password for bootstrap runs | `toolbox-clouds-yaml` |

## Key choices and their consequences

| Choice | Alternative(s) | Why one would choose it | Consequence in operation |
|---|---|---|---|
| One skip-level upgrade, 2025.1 to 2026.1 | Two upgrades, through 2025.2 | One maintenance window; supported for SLURP releases | Every change above arrives at once; RabbitMQ may need an intermediate version |
| Two upgrades through 2025.2 | Skip-level | Smaller steps, each with fewer changes to check | Two maintenance windows, and twice the release notes to check; 2025.2 is not a SLURP release, so from it the next upgrade can only go one release ahead |

## Version notes

### Steps, as the 2026.1 operating guide gives them

> ⚠️ **State-changing.** `kolla-ansible upgrade` recreates every container from the new images and runs the database
> schema migrations; services restart. The guide asks for a backup of the configuration directory first; plan a
> database backup too. Try the upgrade on a lab with the same inventory structure before production.

1. Back up the configuration directory (`/etc/kolla` by default).
2. Upgrade the `kolla-ansible` package; for a skip-level upgrade, upgrade Ansible to a version 2026.1 supports.
3. `kolla-ansible install-deps`.
4. Compare your inventory with the 2026.1 sample inventory and apply the inventory changes above.
5. Update `globals.yml` from the release notes; merge `passwords.yml` with `kolla-genpwd` and `kolla-mergepwd`.
6. `kolla-ansible pull`, then `kolla-ansible prechecks`.
7. Check the RabbitMQ upgrade path (the skip-level preparation section of the guide).
8. `kolla-ansible upgrade`.

```bash
kolla-ansible pull -i <inventory>
kolla-ansible prechecks -i <inventory>
kolla-ansible upgrade -i <inventory>
```

The 2026.1 operating guide links its skip-level preparation to a "RabbitMQ SLURP section" of the RabbitMQ guide;
the 2026.1 RabbitMQ guide describes the allowed upgrade paths under "Upgrading RabbitMQ" instead.

## Lessons learned

No first-hand lessons yet. From the release notes, the changes most likely to stop an upgrade are the inventory
group renames (`kolla_toolbox`, `kolla_logs`), the Cinder group move for LVM users, the Valkey switch, the
Ansible version and the host operating system.

## Validity and limits

Built from the release notes in the Kolla-Ansible source: notes on `stable/2026.1` and not on `stable/2025.1`.
That method has two limits:

- a change backported to 2025.1 appears on both branches and is not listed here (for example, Valkey support itself
  already exists on 2025.1);
- it does not tell whether a change came with 2025.2 or with 2026.1; for a skip-level upgrade both apply.

Only upgrade, deprecation and prelude sections were reviewed in full; new features and bug fixes are not listed.
Not applied on a platform.
