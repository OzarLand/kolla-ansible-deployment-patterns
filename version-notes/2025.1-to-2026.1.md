# From 2025.1 to 2026.1. What changes for a Kolla-Ansible deployment, from the release notes

> 🛑 An upgrade is a destructive operation on the whole platform. This playbook is built from the release notes and
> followed once on a disposable all-in-one lab. Check the upstream release notes and the Kolla-Ansible operating guide
> for your own platform before following any step.

**See also:** [Upgrading an all-in-one lab from 2025.1 to 2026.1, what happened](upgrade-report-2025.1-to-2026.1-all-in-one-lab.md).

## Upgrade path

2025.1 and 2026.1 are both SLURP releases (the OpenStack
[release cadence resolution](https://governance.openstack.org/tc/resolutions/20220210-release-cadence-adjustment.html)),
so a deployment can go from one to the other in a single skip-level upgrade; the Kolla-Ansible
[operating guide for 2026.1](https://docs.openstack.org/kolla-ansible/2026.1/user/operating-kolla.html) describes the
extra preparation. Everything released in between, in the 2025.2 (Flamingo) and 2026.1 cycles, reaches the
deployment at once.

This page lists what a 2025.1 deployment meets on the way, grouped by what the operator has to do. It is built from
the release notes in the Kolla-Ansible source: the notes present on the `stable/2026.1` branch and absent from
`stable/2025.1`, read one by one (97 files), together with the 2025.2 and 2026.1 preludes, the 2026.1 operating
guide, support matrix and sample inventory.

These steps were then followed on a disposable all-in-one lab, from 2025.1 (Kolla-Ansible 20.6.0) to 2026.1
(Kolla-Ansible 22.2.0); the [lab review](https://github.com/OzarLand/kolla-ansible-deployment-patterns/pull/11#issuecomment-6351817451) and the [experience report](upgrade-report-2025.1-to-2026.1-all-in-one-lab.md) give what happened, and the
corrections are folded in below. More first-hand reports are wanted, above all from multinode deployments: see
[issue #6](https://github.com/OzarLand/kolla-ansible-deployment-patterns/issues/6).

| Choice | Alternative(s) | Why one would choose it | Consequence in operation |
|---|---|---|---|
| One skip-level upgrade, 2025.1 to 2026.1 | Two upgrades, through 2025.2 | One maintenance window; supported for SLURP releases | Every change above arrives at once; RabbitMQ may need an intermediate version |
| Two upgrades through 2025.2 | Skip-level | Smaller steps, each with fewer changes to check | Two maintenance windows, and twice the release notes to check; 2025.2 is not a SLURP release, so from it the next upgrade can only go one release ahead |

## Go / no-go checklist

Go only when every line holds. Each one points to the row or step below that explains it.

- [ ] Every host runs an OS that 2026.1 supports: CentOS Stream 10, Debian 13, Rocky Linux 10 or Ubuntu 24.04
  (`doc/source/user/support-matrix.rst` in stable/2026.1; no Rocky Linux 9 or CentOS Stream 9, and Debian 12 is not
  in the matrix although the host OS precheck still accepts `bookworm`).
- [ ] No Linux Bridge mechanism driver: the deployment runs ML2/OVS or ML2/OVN.
- [ ] No dropped service left: Zun, Kuryr, InfluxDB, Telegraf, Venus, VMware drivers, `ironic-inspector`.
- [ ] The inventory carries the renamed groups `kolla_toolbox` and `kolla_logs`, and the new Neutron groups.
- [ ] With Cinder LVM, the volume service is mapped to the hosts that hold the volume group (`cinder-volume-lvm`).
- [ ] Redis replaced by Valkey in `globals.yml` (`enable_redis: "no"`, `enable_valkey: "yes"`), if Redis was enabled.
- [ ] The RabbitMQ version path from the running version to 2026.1's is allowed (`rabbitmq_allowed_upgrades`).
- [ ] Ansible on the deployment host is a version 2026.1 supports (Ansible 12 to 13, ansible-core 2.19 to 2.20).
- [ ] A database backup taken, copied off the hosts, and **restored once on a scratch host**, with the configuration
  directory backed up next to it.
- [ ] Disk space for two sets of images on every host until the old ones are removed (about 7 GB more on the
  all-in-one lab).
- [ ] The health checks below pass on 2025.1.

## Prerequisites and pre-checks

Run these on the running 2025.1 platform; repeat them after the upgrade (see [Health checks](#health-checks)).

```bash
# Galera: cluster size equals the number of MariaDB nodes, the node is Synced, the cluster is Primary
docker exec -it mariadb mariadb -uroot -p -e "SHOW STATUS LIKE 'wsrep_cluster_size'; SHOW STATUS LIKE 'wsrep_local_state_comment'; SHOW STATUS LIKE 'wsrep_cluster_status';"

# RabbitMQ: every node running, no partitions, no alarms
docker exec rabbitmq rabbitmqctl cluster_status

# Nova: the upgrade readiness checks of the running release
docker exec nova_api nova-status upgrade check
```

- `-it` lets `-p` prompt for the MariaDB root password: `database_password` in `passwords.yml`. With a single
  MariaDB node, the cluster size is 1.
- `nova-status upgrade check` returns 0 when every check passes, 1 when there are warnings to read, and 2 or more on
  a failure ([nova-status](https://docs.openstack.org/nova/2026.1/cli/nova-status.html)). During the upgrade,
  Kolla-Ansible 2026.1 runs it again with the new Nova image before upgrading Nova, and stops on a code other than
  0 or 1 (`ansible/roles/nova/tasks/upgrade.yml`).
- Galera status variables: MariaDB's [Galera cluster status variables](https://mariadb.com/kb/en/galera-cluster-status-variables/);
  RabbitMQ cluster status: [clustering guide](https://www.rabbitmq.com/docs/clustering).

## Differences between the releases that mattered

### Before the upgrade: what must change

| Change | What to do | Release note |
|---|---|---|
| Ansible: 2025.1 supports Ansible 10 to 11 (ansible-core 2.17 to 2.18); 2026.1 supports Ansible 12 to 13 (ansible-core 2.19 to 2.20) | Upgrade Ansible on the deployment host; the operating guide says to do it explicitly for a skip-level upgrade, then run `kolla-ansible install-deps` | `ansible-2.19`, `ansible-2.20` |
| Host operating systems: 2026.1 supports CentOS Stream 10, Debian 13 (Trixie), Rocky Linux 10 and Ubuntu 24.04 (stable/2026.1 `doc/source/user/support-matrix.rst`); its host OS precheck (`ansible/roles/prechecks/vars/main.yml`, `host_os_distributions`) accepts CentOS 10, Debian `bookworm` and `trixie`, Rocky 10 and Ubuntu `noble`. 2025.1 supports CentOS Stream 9 and 10, Debian 12 (Bookworm), Rocky Linux 9 and 10 and Ubuntu 24.04 (stable/2025.1 `doc/source/user/support-matrix.rst` and `host_os_distributions`) | Move hosts on Rocky Linux 9, CentOS Stream 9 or Debian 12 to a supported OS first (Debian 12 passes the precheck but is not in the 2026.1 matrix) | Support matrices of both releases |
| Inventory: group `kolla-toolbox` renamed `kolla_toolbox`; the `common` role renamed `kolla_toolbox` | Rename the group in your inventory and overrides | `rename-kolla-toolbox-role` |
| Inventory: group `kolla-logs` renamed `kolla_logs` (log collection split from `common`); `cron` and `fluentd` have their own roles | Rename the group, as in the 2026.1 sample inventory | `kolla-logs-rename`, `cron-break-out-role`, `fluentd-break-out-role` |
| Cinder: `cinder-volume` and `cinder-backup` now default to the `cinder` group (the controllers) instead of `storage`; new groups `cinder-volume-lvm`, `cinder-volume-multiple`, `cinder-backup-lvm`, `cinder-backup-multiple` | Update inventory overrides; LVM users keep the volume service on the hosts that hold the volume group | `move-cinder-volume` |
| Redis replaced by Valkey | Set `enable_redis: "no"` and `enable_valkey: "yes"` in `globals.yml` before the upgrade; the playbooks migrate the data | `replace-redis-with-valkey` |
| RabbitMQ: upgrades are limited to allowed version paths (`rabbitmq_allowed_upgrades`, for example 3.13 to 4.0, 4.1 or 4.2); a skip-level upgrade may need an intermediate RabbitMQ version | Check the allowed path before upgrading; the `rabbitmq-version-check` task fails with the next intermediate version otherwise | `rabbitmq-42`; RabbitMQ guide |
| Linux Bridge mechanism driver removed, already removed from Neutron | Migrate to ML2/OVS or ML2/OVN before the upgrade | `remove-neutron-linuxbridge` |
| Services dropped: Zun and Kuryr, InfluxDB, Telegraf, Venus, VMware drivers, `ironic-inspector`; legacy (non-rolling) Ironic upgrade | Remove them from the deployment first. Not covered here: Kolla-Ansible has no command that removes a single service (the 2026.1 command list has `stop` and `destroy`, which act on the whole deployment), and the release notes only say that InfluxDB and Telegraf containers and configuration are to be removed manually. Removing a service deletes its containers and may delete its data and database; plan it per service, on a lab first | `drop-kuryr-and-zun`, `drop-influxdb-telegraf`, `drop-venus`, `drop-vmware-support`, `drop-ironic-inspector`, `ironic-drop-legacy` |
| Variables renamed or removed: `lightbits_JWT` → `lightbits_jwt`; `ironic_inspector_kernel_cmdline_extras` → `ironic_kernel_cmdline_extras`; `ironic_inspector_pxe_filter` → `ironic_pxe_filter`; `bifrost_enable_ironic_inspector`, `distro_python_version` and `neutron_legacy_iptables` removed | Update `globals.yml` and overrides | `lightbits-jwt`, `drop-ironic-inspector`, `remove-distro-python-version`, `drop-legacy-iptables` |
| Local changes to the log-rotation cron templates | Re-apply them on the simplified templates | `simplified-cron-templates` |

### What changes by itself during the upgrade

| Change | Consequence to expect | Release note |
|---|---|---|
| MariaDB through HAProxy and `clustercheck` is no longer supported | `kolla-ansible upgrade` deploys ProxySQL and removes the `clustercheck` containers. ProxySQL was already the default in 2025.1 (`enable_proxysql: "yes"`, release note [`switch-to-proxysql`](https://opendev.org/openstack/kolla-ansible/src/branch/stable/2025.1/releasenotes/notes/switch-to-proxysql-907c2bc2f2c04de4.yaml), absent from 2024.2); in 2026.1 it follows `enable_mariadb`. An explicit `enable_proxysql: "no"` is still honoured: on the lab, the upgrade removed `mariadb_clustercheck`, deployed no ProxySQL, and the services kept reaching MariaDB directly. A deployment that relied on HAProxy in front of MariaDB was not tested | `drop-clustercheck-and-haproxy-support-for-mariadb` |
| All API services under uWSGI, Apache WSGI support dropped | `glance-tls-proxy` and `neutron-tls-proxy` disappear; TLS is terminated by uWSGI | `uwsgi-glance`, `neutron-uwsgi`, `barbican-uwsgi`, `uwsgi-designate`, `uwsgi-magnum` |
| Neutron follows the upstream layout | New containers `neutron-rpc-server`, `neutron-periodic-workers`, `neutron-ovn-maintenance-worker`, with new inventory groups `neutron-rpc-server`, `neutron-periodic-worker` and `neutron-ovn-maintenance-worker` in the 2026.1 sample (step 4). The lab saw `neutron_rpc_server` and `neutron_periodic_worker` appear on ML2/OVS | `neutron-uwsgi` |
| Neutron agent wrappers on by default | DHCP, L3 and related agents restart without respawning the main containers; set `neutron_agents_wrappers: "no"` for the old behaviour | `neutron-agent-wrappers-by-default` |
| Horizon behind HAProxy listens on port 8080 | Firewall rules or monitoring that target Horizon's backend port need updating. Without HAProxy, Horizon stays on port 80 (observed on the lab) | `horizon-port` |
| ML2/OVS L3 HA no longer sets `ha_vrrp_health_check_interval` | Different failover behaviour when the router's health checks were relied on | `diable_ha_vrrp_health_check_interval` |
| `om_rabbitmq_qos_prefetch_count` raised to 50 | Different message flow per consumer | `qos_prefetch_count_bump` |
| Enterprise Linux hosts: HAProxy and RabbitMQ trust `ca-bundle.crt` instead of `ca-bundle.trust.crt` | Check custom CA handling on EL hosts | `ca-bundle-trust` |
| Horizon session cache uses Valkey when it is enabled | Session behaviour changes with Valkey | `bug-2093414` |
| `kolla-toolbox` uses `clouds.yaml` | `openstack_auth` only carries the Keystone admin password for bootstrap runs | `toolbox-clouds-yaml` |
| Component versions in the images (observed on the lab, with the `2025.1-ubuntu-noble` and `2026.1-ubuntu-noble` images of October 2026) | **MariaDB 10.11 → 11.4.13**, a major version: check database tooling, clients and monitoring. RabbitMQ 4.0.9 → 4.2.9. Nova API maximum microversion 2.100 → 2.103. The MariaDB jump went through without incident on the lab | Lab review; not in the release notes reviewed |

## Procedure

### Upgrade steps, as the 2026.1 operating guide gives them

> 🛑 **Destructive.** `kolla-ansible upgrade` recreates every container from the new images and runs the database
> schema migrations of every service. The migrations cannot be rolled back: the 2025.1 images do not run against a
> 2026.1 schema, so **what is lost is the way back to 2025.1** without a restore. Services restart during the
> upgrade. Precondition: a database backup and the configuration backup of step 1, both checked (readable, complete,
> copied off the hosts). Undo: restore the databases and the configuration directory from those backups, and
> redeploy the 2025.1 images. Try the upgrade on a lab with the same inventory structure before production.

1. Back up the configuration directory (`/etc/kolla` by default), the inventory, and the databases. Kolla-Ansible's own backup
   needs `enable_mariabackup: true` and a `kolla-ansible reconfigure -t mariadb` first, then
   `kolla-ansible mariadb-backup -i <inventory>`; the backup lands in the `mariadb_backup` Docker volume on the
   first MariaDB node, to be copied elsewhere ([MariaDB backup and restore](https://docs.openstack.org/kolla-ansible/2025.1/admin/mariadb-backup-and-restore.html)).
   The 2025.1 guide writes the command `mariadb_backup`; the 2025.1 command-line tool registers it as
   `mariadb-backup`.

   > ⚠️ **State-changing.** `reconfigure -t mariadb` can restart the MariaDB containers. Run it inside the
   > maintenance window, not the day before.

   What the backup looks like, as the lab found it: a **directory** `full-<date>-<id>/` holding
   `mysqlbackup-<id>.qp.xbc.xbs.gz`, in a volume only root can read. Check it before going further, with a check
   that fails loudly when it finds nothing: copy the directory with `sudo`, run `gzip -t` on the file, then extract
   it with `mbstream -x` into a scratch directory (for example inside the running `mariadb` container). Every
   service database must appear, and `xtrabackup_checkpoints` must say `backup_type = full-backuped`. Copy the
   backup off the host with its checksum.
2. Install the 2026.1 `kolla-ansible` package, with an Ansible version 2026.1 supports, in a **new** virtual
   environment, and keep the 2025.1 one until the upgraded platform is checked: it is the way back before step 8.
   (The lab upgraded in place, in the same virtual environment; that works, but leaves no previous environment.)
3. `kolla-ansible install-deps`.
4. Compare your inventory with the 2026.1 sample inventory and apply the inventory changes above.
5. Update `globals.yml` from the release notes; merge `passwords.yml` with `kolla-genpwd` and `kolla-mergepwd`.
   If the upgrade changes anything in Docker's own configuration (a new image registry, an insecure plain-HTTP
   registry, a proxy), apply it now: `kolla-ansible upgrade` does not, and `docker_registry_insecure` and the other
   Docker settings only reach the daemon through `bootstrap-servers`. Either run `bootstrap-servers`, which can
   restart Docker and every container with it, or change `/etc/docker/daemon.json` by hand. Then check what the
   daemon really uses with `docker info` (proxy, insecure registries).

   > ⚠️ **State-changing.** On the lab, adding the registry to `insecure-registries` and running
   > `sudo systemctl reload docker` applied it without restarting any container. A `systemctl restart docker`
   > restarts every container on the host.
6. `kolla-ansible pull`, then `kolla-ansible prechecks`.
7. Check the RabbitMQ upgrade path (the skip-level preparation section of the guide).
8. `kolla-ansible upgrade`.
9. After checking the platform, remove the old images. Plan disk space for two sets of images until then.

```bash
kolla-ansible pull -i <inventory>
kolla-ansible prechecks -i <inventory>
kolla-ansible upgrade -i <inventory>
```

`kolla-ansible prune-images` prunes Kolla images (filter on the `kolla_version` label) with Docker's prune, which by
default removes only dangling images: on the lab it removed none of the 30 still-tagged `2025.1` images. Remove
them by tag.

> ⚠️ **State-changing.** Removing the old images frees disk space (about 7 GB on the all-in-one lab) but removes
> the quickest way back: a return to 2025.1 then needs the images pulled again, on top of the database and
> configuration restore. Do it once the upgraded platform is checked. Running containers are not affected.

```bash
docker images --format '{{.Repository}}:{{.Tag}}' | grep ':2025.1-'          # list first
docker images --format '{{.Repository}}:{{.Tag}}' | grep ':2025.1-' | xargs -r docker rmi
```

The 2026.1 operating guide links its skip-level preparation to a "RabbitMQ SLURP section" of the RabbitMQ guide;
the 2026.1 RabbitMQ guide describes the allowed upgrade paths under "Upgrading RabbitMQ" instead.

### What Kolla-Ansible does by itself during `upgrade`

- **Online data migrations:** after the services are upgraded, Kolla-Ansible 2026.1 runs Nova's online data
  migrations for the API database and for each cell (plays "Run Nova API online data migrations" and "Run Nova cell
  online data migrations" in `ansible/nova.yml`), and the equivalent step for Cinder, Placement and Ironic. You do not
  run `nova-manage db online_data_migrations` by hand. See Nova's
  [upgrades guide](https://docs.openstack.org/nova/2026.1/admin/upgrades.html) for what they do.
- **Nova upgrade check:** run before upgrading Nova, as above.

```bash
# the same three checks, now on 2026.1

```

> network.

```bash

openstack server delete --wait upgrade-check
```

On the lab, `kolla-ansible check` also passed after the upgrade.

## Problems met and how they were resolved

On the all-in-one lab, `kolla-ansible upgrade` itself completed on the first run (24 minutes, `failed=0`). Running
instances never stopped; floating IPs lost one 2 s gap when `openvswitch_vswitchd` was recreated; APIs were
unavailable for up to about 30 s each while their containers were recreated. What went wrong happened before the
upgrade command, and the steps below now cover it:

- the 2026.1 `pull` failed (`http: server gave HTTP response to HTTPS client`) because the new registry was plain
  HTTP and Docker's daemon settings had not been updated (step 5);
- the first check of the database backup checked nothing, because the backup is a directory, not a single file
  (step 1);
- `kolla-ansible prune-images` left the 30 old images (about 7 GB) in place (step 9).

Details in the [experience report](upgrade-report-2025.1-to-2026.1-all-in-one-lab.md).

## Rollback

There is no downgrade. The database schema migrations and the online data migrations of `kolla-ansible upgrade`
cannot be undone, and the 2025.1 images do not run against a 2026.1 schema.

- **Before step 8:** nothing on the platform has changed yet, apart from the Ansible and `kolla-ansible` versions on
  the deployment host, the inventory and `/etc/kolla` (steps 4 and 5) and, if done, Docker's daemon settings. Go
  back to the 2025.1 virtual environment kept in step 2; if it was upgraded in place, reinstall the 2025.1 versions
  (`kolla-ansible` 20.x and the Ansible version it requires). Restore the inventory and `/etc/kolla` from the
  backup of step 1, and undo the Docker daemon change if one was made.
- **After step 8:** going back means restoring the databases and the configuration directory from the backups of
  step 1, and redeploying the 2025.1 images. Everything done on the platform since the backup is lost. This is why the
  checklist asks for a backup restored once beforehand.
- **After step 9:** the old images are gone too; they must be pulled again before a redeploy.

## Lessons learned

From the release notes, the changes most likely to stop an upgrade are the inventory group renames
(`kolla_toolbox`, `kolla_logs`), the Cinder group move for LVM users, the Valkey switch, the Ansible version and the
host operating system. From the all-in-one lab run: what goes wrong tends to happen before `kolla-ansible upgrade`
(Docker's own settings, the backup check); check the daemon with `docker info` and the backup's content, not only
that files exist.

## Validity and limits

Built from the release notes in the Kolla-Ansible source: notes on `stable/2026.1` and not on `stable/2025.1`.
That method has two limits:

- a change backported to 2025.1 appears on both branches and is not listed here (for example, Valkey support itself
  already exists on 2025.1);
- it does not tell whether a change came with 2025.2 or with 2026.1; for a skip-level upgrade both apply.

Only upgrade, deprecation and prelude sections were reviewed in full; new features and bug fixes are not listed.

Followed once, on a disposable all-in-one lab (Kolla-Ansible 20.6.0 to 22.2.0, Ubuntu 24.04, ML2/OVS, no HAProxy,
no ProxySQL, no Cinder, no Redis or Valkey): see the [lab review](https://github.com/OzarLand/kolla-ansible-deployment-patterns/pull/11#issuecomment-6351817451) and the
[experience report](upgrade-report-2025.1-to-2026.1-all-in-one-lab.md). Not tested: multinode deployments with HAProxy, Cinder, Valkey migration, Linux
Bridge migration, dropped services, other host operating systems. The component versions observed depend on the
images' build date.
